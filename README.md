# IEEE SPS Committee Copilot

A working tool for an IEEE Signal Processing Society student branch chapter committee:
find conferences worth bringing to campus, get grounded feedback on event ideas, run the
outreach, plan the event, and produce the annual report.

Runs on your own machine. No account, no hosting, no API key required to start.

---

## What it does

### 1. Conference tracker and alerts
Crawls the IEEE SPS site and WikiCFP daily, scores every event for how worth approaching
it is, and pushes the good ones to Telegram and email.

The score is the point. It answers *"should we contact these organisers about hosting
this?"* out of 100, and every point is explained:

| Component | Weight | What it measures |
|---|---:|---|
| Opportunity | 35 | Is there an actual opening to host or co-host? |
| Topic | 25 | Is it genuinely signal processing? |
| Proximity | 20 | Can our people and our Section realistically reach it? |
| Lead time | 12 | Is there runway left to bid and organise? |
| Scale | 8 | Can our venue physically hold it? |
| Quality | −25 | Penalty for predatory and aggregator-spam listings |

Opportunity outweighs topic deliberately. A perfectly on-topic conference that has already
picked its venue is not actionable; an open **Call for Organizers** is, even if its theme is
only adjacent. The highest-value feed is the SPS *Call for Organizers* page, where IEEE
publicly asks for volunteers to host a conference — that is the literal front door to
bringing one to your campus, and it ranks first by design.

### 2. Event advisor (chat)
Pitch an idea or a cross-society collaboration and get structured feedback: verdict and
score, strengths, risks, comparable past SPS events with links, the right format with real
budget and lead-time figures, which sister society to co-host with and the argument that
wins them over, and an ordered list of next steps.

Grounding comes from ~100 real past IEEE SPS events harvested from the Society's own event
archive, plus curated data on IEEE programmes. Budgets and funding routes are **never**
generated by the model — they come from `data/knowledge/event_formats.json` — so the numbers
stay defensible in front of a faculty advisor.

There is also a free-form chat tab for follow-up questions.

### 3. Outreach pipeline
Tracks each conference from `identified` → `researching` → `contacted` → `in_conversation`
→ `proposal_sent` → `committed`, drafts the actual introduction email (tailored to whether
they are asking for hosts or not), stores contacts and notes, and sets a follow-up date
automatically so nothing stalls silently.

### 4. Deadline radar
The dates that actually bind you — hosting-proposal windows, CFP cutoffs, follow-ups you
committed to — in one list, with the near ones marked. Filtered so aggregator noise cannot
bury a real deadline.

### 5. Event playbook generator
Turns an approved pitch into an executable plan: itemised budget that sums exactly, a
working-backwards timeline, committee role split, the IEEE approvals with long lead times,
a promotion schedule, and (with an LLM) a run sheet, speaker profiles and sponsor targets.
Exports as Markdown.

### 6. Chapter activity report
Log events as you run them; the annual report becomes a query instead of an archaeology
project. Produces a Markdown report and a CSV for pasting into IEEE reporting forms.

## Deploying it for a committee

See **[DEPLOY.md](DEPLOY.md)** — free Postgres (Neon) + Streamlit Community Cloud +
a GitHub Actions cron, about 20 minutes. The scheduled crawl runs in CI because a
free-tier hosted UI sleeps when nobody is looking at it, which would silently stop
the alerts.

Committee-facing instructions in plain language are a separate one-page guide.

## Quick start

```powershell
python -m pip install -r requirements.txt
Copy-Item .env.example .env      # then edit it - see below
./run.ps1
```

`run.ps1` starts the API on <http://127.0.0.1:8000> (docs at `/docs`) and the UI on
<http://localhost:8501>.

First run: open **Settings → Run a crawl now**, then **Refresh past-event knowledge**.

### Minimum configuration

Everything works with no keys at all. The only settings that really matter at the start are
who you are, because they drive the fit score and the outreach letters:

```ini
CHAPTER_NAME=IEEE SPS Student Branch Chapter, <your college>
INSTITUTION=Your Institute of Technology
CITY=Your City
COUNTRY=India
IEEE_SECTION=Your IEEE Section
CHAIR_NAME=Your Name
CHAIR_EMAIL=you@example.com
VENUE_CAPACITY=500
```

Change any of these later and press **Rescore everything** in Settings — proximity and
scale are recomputed for every tracked event.

## Optional integrations

### LLM (better written feedback, drafted emails, run sheets)
Pluggable, Gemini by default:

```ini
LLM_PROVIDER=gemini          # gemini | claude | none
GEMINI_API_KEY=...
GEMINI_MAX_RPM=5             # free tier is ~5 requests/minute
GEMINI_MAX_RETRIES=1         # each retry costs a request from a small daily quota
```

To use Claude instead, set `LLM_PROVIDER=claude` and `ANTHROPIC_API_KEY`.

Every LLM response is cached on disk by prompt hash and calls are self-throttled, because
the Google free tier has a small daily budget. If the quota runs out the app **does not
break** — it falls back to rules-only output for the rest of the session and says so.

### Telegram alerts
1. Create a bot with [@BotFather](https://t.me/BotFather), put the token in `TELEGRAM_BOT_TOKEN`
2. Add the bot to your committee group and send any message there
3. Settings → **Find chat id**, copy it into `TELEGRAM_CHAT_ID`

### Email digest
```ini
SMTP_USER=you@gmail.com
SMTP_PASSWORD=<app password, not your account password>
DIGEST_TO=chair@…,secretary@…,advisor@…
```

### Schedule
```ini
CRAWL_HOUR=7        # daily crawl, local hour
DIGEST_DAY=0        # 0=Mon … 6=Sun
DIGEST_HOUR=9
ALERT_THRESHOLD=70  # instant alert at or above this fit score
```

## Layout

```
backend/
  main.py          FastAPI app and all endpoints
  config.py        env-backed settings, everything has a default
  store.py         SQLite persistence + migrations
  scoring.py       the fit score, with explanations
  crawler.py       collect → score → store, one bad source never kills a run
  radar.py         deadline aggregation and urgency
  advisor.py       pitch evaluation + chat, LLM and rules paths
  playbook.py      budgets, timelines, roles, approvals
  outreach.py      pipeline stages and email drafting
  reporter.py      annual activity report (Markdown + CSV)
  knowledge.py     grounding corpus + TF-IDF retrieval
  llm.py           pluggable Gemini/Claude with throttling, caching, fallback
  scheduler.py     daily crawl, weekly digest, monthly archive refresh
  sources/         sps.py, wikicfp.py, base.py (fetch/parse/date helpers)
  notify/          telegram.py, mailer.py, digest.py
data/knowledge/    event_formats.json, ieee_societies.json, past_events.json
frontend/app.py    Streamlit UI
```

## Source coverage, honestly

Automated discovery works well for SPS-run events worldwide. It is **weak for
India-specific IEEE conferences**, and that is a limitation of the sources, not of the
scoring:

| Source | Status |
|---|---|
| SPS site, incl. Call for Organizers | Works — the primary feed |
| WikiCFP topic browse + regional search | Works; thin India coverage |
| `ieee.org` conference search | Blocked — bot protection returns an empty `202` |
| IEEE India Council / Bangalore Section events API | Plugin installed but no events published |
| India Council "Conferences in India" page | Stale — last updated 2021 |

So the tracker has a **manual add** form (Conference tracker → *Add a conference manually*).
Regional leads usually reach a chair through a Section mailing list, a faculty contact or a
WhatsApp group well before any crawler would see them. Anything added by hand is scored,
tracked, put on the radar and worked through outreach exactly like a crawled record.

The regional WikiCFP searches are generated from `CITY` and `COUNTRY` in your `.env`, so
they re-target automatically if the chapter profile changes.

## Notes on the data sources

- **SPS site** (`signalprocessingsociety.org`) is a Drupal site; the collector parses
  `<article>` listing rows and falls back to each event's detail page to fill in missing
  dates and locations. Four feeds: call for organizers, upcoming calendar, calls for
  papers, and the event archive (used only as advisor grounding).
- **WikiCFP** is fetched over HTTP with an automatic HTTPS→HTTP fallback, because some
  Windows Python builds reject its TLS chain. Its listings include journals and predatory
  conferences, which the quality penalty in `scoring.py` pushes down.
- Pages are cached on disk for 6 hours, so re-running a crawl during a working session is
  cheap and polite to the upstream sites.

## Adding a source

Write a module in `backend/sources/` exposing `collect(use_cache=True) -> list[dict]` with
`uid`, `source` and `title` set, then register it in `crawler.SOURCES`. Scoring, storage,
alerting and the radar pick it up with no other changes.
